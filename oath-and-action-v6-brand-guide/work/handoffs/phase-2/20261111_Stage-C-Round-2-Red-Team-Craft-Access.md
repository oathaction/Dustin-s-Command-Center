## Must fix

**M1. Chapter 18, Rule 18.14, code set `c-18-download`, both live stages: pressing the download that "works" sends the whole guide to an error page.** The caption reads "A download that works and one that is not ready, live." The first link reads "Download tokens.css, CSS, 93 KB", with `href="tokens.css"` and `download="20261106_Oath-And-Action-Tokens.css"`. No such file sits beside the guide, so in Chromium a press navigated the page to `chrome-error://chromewebdata/`; on the hosted preview the relative address would find no file either. A reader who tries the live demo loses their place in a 9.5 MB page, and the demo teaches nothing. D2-1486 chose the relative link so the stage shows the link as a builder ships it; that stays right for the code panel, and wrong for the live stage. Fix: in the live stages only, the build marks this link `data-oa-file` so the shell's download script (D2-1500) serves the page's own tokens.css data URI, as the colophon's link does; the HTML panel keeps `href="tokens.css"`. Add the live stage's download to the guide check's download test. Owners: engineer (build and shell), component engineer (the set's note if its markup changes).

**M2. Chapter 26, Rule 26.7, `s-26-token-table` (D2-1529): the table stacks every row at every width, so it runs 175,377 px at 1440.** Measured: the plate is 175,377 px tall at 1440, 175,269 at 1280, 176,690 at 1024 and 183,802 at 390, with a median row of 354 px at desktop. That is 18 percent of the guide's 956,189 px and most of chapter 26's 212,034 px, which makes chapter 26 the longest chapter in the guide. Reading it end to end means scrolling about 195 screens of 900 px. In the stacked rows the name cell keeps the table's 256 px column width, so CSS names break in the middle of a 722 px card with room to spare: "--oa-color-state-empty-edge-" on one line and "on-white" on the next, and "oa.color.state.empty.edge." over "onWhite". Search, the status line and Copy all work (see Tested), so look-up by search is sound; reading the table is not. My judgment on D2-1529: neither stacked rows at desktop nor the break-out alone. A break-out over the rail helps only from 1280 px, still leaves a table of roughly 35,000 px, and leaves 1024 stacked. Fix: (1) lay the table out as a table whenever its own width reaches 40rem, in five columns (name with the CSS name and Copy under it, value with its swatch, use, tier, contrast), which fits the 722 px stage at 1024 and up; (2) put each category in a disclosure, closed by default, that shows its count ("Color: the palette (7)"), and let search open every group that holds a match, so the plate opens at about thirty group heads; (3) let a name break only at its dots or hyphens when it truly does not fit, never inside a cell with room. Owner: engineer (`token_table_build.py`, `stage_c_ch26_build.py`).

## Should fix

**S1. `codeMatch`'s tolerance (D2-1526): the code allows 64, the log says 49, and no pixel tolerance can police thin marks.** `guide_check.js` sets `const EDGE_TOL = 64` (line 1212); D2-1519 records 64, while D2-1526 and the comment above the constant say "up to 49 of 255". I reran `codeMatch`'s own capture and comparison, copied from the check, with a fault planted in the pasted copy only:
- As built, four stages differ by at most 41 (table, dark), 26, 22 and 17.
- Error words and every table cell drawn in `--oa-color-text-secondary` on Charcoal, Dim Newsprint for Newsprint, so the text falls from 13.29 to 1 to 7.26: **passes at 64**, caught at 49 (largest pixel difference 57).
- The success mark drawn in Stone, the muted mark's color, for Verdigris: **passes at 64, 49 and 32** (largest difference 38 on Newsprint, 27 on Charcoal). A 1.5 px line has no flat pixels, so every pixel counts as an edge.
- Row rules in Deep Stone for Stone pass at every tolerance, and 754 differing pixels sat on the capture's outer ring, which the check never compares.
- Text at weight 500 for 400, and row rules removed, are caught.
So yes, an edge difference of up to 49 can hide a fault a reader would see: a success that reads as muted, or a keyline in the wrong token. I would set the pixel tolerance at 49, the measured antialiasing maximum the log already records, and stop asking pixels to catch color. Add a computed-style comparison: for every element of each live stage and of its pasted copy, compare `color`, `background-color`, the four border colors and widths, `outline-color`, `fill`, `stroke`, `font-family`, `font-size`, `font-weight`, `letter-spacing` and `line-height`, and fail any difference. I ran that comparison here: on fourteen sets it reported no difference, on the filter bar and search it found S6's spans, which no pixel test can see, and it took seconds. Owner: engineer.

**S2. Chapter 18, every code plate: the code panels scroll both ways, so a builder reads code through a keyhole.** Each panel is `white-space: pre`, 867 px wide at 1440 and capped at 448 px tall. Measured line widths: the masthead's HTML panel runs 27,922 px (the wordmark's inline SVG on one line), the table's HTML 8,763, the loop stepper's 6,917, the link's 6,572, the filter bar's 6,395; every CSS panel runs 1,397 to 2,239 px, and most scripts over 1,000. The tabs' CSS is 720 px of code shown in 448. At 390 about 38 characters of each line show. Rule 18.12 is the guide's own rule for showing code, and the guide's panels are the hardest code in it to read. The panels' group names also say only "at true size. Scroll sideways to see all of it." when they scroll down as well. Fix: write each CSS rule one declaration per line and break long attributes and SVG path data onto their own lines (the copy then reads as well as it runs); let a panel show up to about 40 lines before it scrolls; and name a panel that scrolls both ways for both. Owners: component engineer (formatting in `c-18-*`), engineer (panel height and names in the shell).

Owner: engineer.

Owners: systems designer (anatomy plates), engineer (chapter 26's examples).

**S8.
